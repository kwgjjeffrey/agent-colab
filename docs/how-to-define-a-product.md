# How to Define a Product

这套方法用于引导产品经理定义一个产品。它不从功能清单或竞品形态开始，而是先说明产品要改变什么工作系统，再逐步得到核心对象、使用循环、交互与指标。

## 1. 描述产品出现前后的系统

先回答：产品出现前，参与者如何完成工作；瓶颈在哪里；产品出现后，参与者之间的关系发生什么变化。

描述应当使用参与者、信息和行动，而不是页面、按钮或技术名词。

例如：

> 之前由人负责在 agent 之间搬运信息；之后由人建立协作关系和决定共享范围，agent 直接获取彼此的工作上下文。

这一步定义产品存在的原因。

## 2. 写出产品定位

定位应回答三个问题：

1. 服务谁；
2. 改变什么；
3. 通过什么核心机制改变。

定位是后续所有讨论的判断标准。评估一个能力时，应问“它能否有效服务定位”，而不是过早用“产品不是什么”画死边界。

类比只能帮助解释陌生概念，不能代替定位。旧产品的类比一旦被提升为定义，后续设计就容易不自觉复制旧时代的信息结构和交互习惯。

## 3. 选择首批真实用户

不要先讨论“所有人”，而要选择一群已经高频遇到这个问题的人，并说明他们每天实际完成什么工作。

首批用户不是永久市场边界，而是产品最先必须成立的地方。一个好的首批用户描述应足以支持后续写出真实故事，而不只是人口属性。

## 4. 找出产品的核心对象

核心对象是用户通过产品持续创建、提供、消费或改变的事物，不是数据库表，也不是页面栏目。

对每个核心对象说明：

- 它由谁产生和拥有；
- 谁将它带入产品关系；
- 谁可以消费；
- 它是静态内容还是持续变化的来源；
- 谁能改变或撤回它。

对象之间的关系如果没有说清楚，功能就会退化成互不相干的按钮。

## 5. 定义参与者，而不只写“用户”

同一个产品可能同时存在贡献者、消费者、管理者、自动化系统和 agent。一个人也可能同时扮演多个角色。

需要说明每个参与者：

- 在什么情况下进入产品；
- 提供什么；
- 取得什么；
- 能作出什么决定；
- 如何与其他参与者共同完成工作。

## 6. 描述持续发生的使用循环

不要从首页开始，先写产品如何进入日常工作：

1. 什么事件触发使用；
2. 用户提供什么；
3. 产品建立或维护什么关系；
4. 其他参与者怎样消费；
5. 消费后产生什么新结果；
6. 新结果如何再次回到循环。

产品价值通常来自循环持续运转，而不是某一次操作完成。

## 7. 分别写三条故事线

当产品同时服务人和 agent 时，应分别写：

### 人类的故事线

人为什么进入、如何判断、提供什么、怎样保持知情、如何退出或撤销。

### Agent 的故事线

Agent 如何发现能力、获得对象清单、逐层读取、执行任务、保留来源和处理变化。

### 人类与 Agent 的故事线

人如何给出判断和授权，agent 如何补充检索与执行，结果怎样被人验收并重新进入协作循环。

三条故事线能够发现单一“用户旅程”容易漏掉的问题，也能避免把人的 GUI 直接翻译成 agent 工具。

## 8. 从故事线推导功能结构

故事线稳定后，再分别设计两套入口：

- GUI：服务人的理解、选择、授权和管理；
- Agent 接口或 Skill：服务 agent 的发现、检索、读取、调用和引用。

每个功能都应该能追溯到故事线中的一个动作。无法追溯的功能先不进入方案；故事线中没有功能承接的动作则说明方案缺失。

## 9. 选择与定位一致的成功指标

不要只测某个局部操作节省几分钟。先问：产品定位如果真正成立，会出现什么可观察行为。

指标需要排除没有产生核心价值的虚假活跃。例如，协作产品中的后台轮询、读取自己的数据或少数重度用户重复调用，都不等于团队协作成立。

## 10. 按阶段延后问题

产品定义阶段解决定位、参与者、对象、关系、场景、使用循环和成功标准。

交互阶段解决功能怎样被人和 agent 使用。技术阶段解决数据、端、服务、通信、性能与可靠性。

延后不是忽略，而是防止页面形态或技术约束反过来替代产品判断。

## 11. 讨论纪律

- 不为保持讨论继续而制造抽象问题；已有明确结论不重复包装成待讨论项。
- 每个问题都应指向真实分歧、缺失决策或可执行的下一步。
- 发现新方向时先记录其价值与未决点；没有想清楚前，不强行并入当前主方案。
- 始终回到定位判断一项设计，而不是依赖预设边界或旧产品类比。
