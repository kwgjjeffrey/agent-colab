# Colab 产品定义草案

状态：讨论中  
阶段：产品定位、场景与用法  
暂不覆盖：交互设计、技术选型、系统架构

## 1. 产品定位

Colab 是面向 agent 协作的上下文共享层。

它通过共享 agent 工作所需的上下文，让不同的人能够通过各自的 agent 共同完成复杂工作，并减少人充当 agent 之间“上下文搬运工”的成本。

今天常见的工作模型是：

> 人 → agent → 环境

当多人协作时，agent 产出信息，人再通过会议、即时通信、文档和手工总结，把信息搬运给另一个人或另一个 agent。agent 的生产速度越高，人的筛选、概括和转述越容易成为瓶颈。

由此产生了一个容易误判的表象：agent 时代的协作不再重要，甚至单人加 agent 比团队更高效。这里的核心判断是，低效的不是协作本身，而是协作链路仍要求人充当 agent 之间的传话筒。

Colab 希望形成新的工作模型：

> 人建立协作关系并登记上下文 → agent 直接获取彼此的工作上下文 → 人与 agent 共同判断和行动

判断一项产品能力是否应该存在，始终只看它能否有效服务这个定位。

## 2. 首批用户

首批用户是一个共同工作的开发团队。

团队每天需要：

- 开发产品；
- 同步信息；
- 协作解决技术问题；
- 完成日常工作总结。

人和 agent 都是 Colab 的直接消费者，其中 agent 是主要消费者。人负责建立和理解协作关系、登记上下文、确认自己正在共享什么，并在需要时为 agent 挑选具体上下文；agent 负责获取频道中的上下文清单，按任务需要继续探索和使用。

## 3. Agent 的工作上下文

当前工作上下文主要来自：

| 来源 | 典型内容 | 当前协作状态 |
| --- | --- | --- |
| 本机文件系统 | 代码、文档、原型、临时分析、未提交产物 | 代码可部分借助 Git；Git 外内容及高频变化共享不足 |
| 本机对话记录 | 用户意图、分析过程、尝试、失败、取舍、工具结果 | 基本被锁在单个会话或产品内，通常只能人工总结搬运 |
| 远端知识与应用 | 企业知识库、数据库、业务系统、接口 | 多人可能访问同一来源，但一次工作实际使用了什么、如何得到结论，仍可能只存在于本机对话中 |

本机文件与对话记录是当前最明显的上下文缺口。Git 能承担一部分文件协作，但它无法覆盖对话，也不适合作为所有工作上下文的高频共享通道。

## 4. Organization：账号与人员目录的边界

Organization 是 SaaS 中的 tenant，也是协作软件中的 team：它回答账号属于哪个协作网络、哪些人可以被搜索和选择，以及企业身份系统如何接入。个人首次注册可拥有一个个人 Organization；企业可通过 OIDC/SSO 把账号自动建立到自己的 Organization。

邀请某人加入 Channel 时，先在当前 Organization 的人员目录搜索。目录内成员可以直接加入；目录外的人需要明确接受邀请，接受后同时成为 Organization 成员和目标 Channel 成员。Organization 管账号与人员关系，Channel 仍然承载实际协作关系，两者不互相替代。

## 5. Channel：协作关系的载体

共享关系围绕 **Channel（频道）** 建立。

人们在现实工作中形成需要持续交换信息的协作关系时，就可以创建 Channel。可以借用上一个时代创建工作群聊的时机来理解“什么情况下需要一个 Channel”，但 Channel 本身不是群聊，Colab 也不沿用群聊的产品模型。

Channel 由参与者按需自行创建，不与 Git 仓库等技术对象一一绑定。例如：

- 一群人为了共同推进某个开发项目创建一个 Channel；
- 一个长期协作的团队创建一个 Channel，用于重要信息同步和日常工作总结；
- 其他任何在传统办公中值得建立工作群聊的协作事项，也可以建立 Channel。

因此，什么时候创建 Channel，不由预设的信息分类规则决定，而取决于现实中是否形成了一个需要持续共享上下文的协作单元。

一个 Channel 聚合：

- 参与协作的人及其 agent；
- 各参与者登记进来的上下文；
- 上下文后续的持续更新；
- 人与 agent 获取、挑选和使用上下文的入口。

Channel 不是一次性的交接包，而是一个持续存在的协作关系。上下文默认持续更新，没有预设时间限制；贡献者可以撤回自己登记的上下文。

### 5.1 Quick Share：不建立协作关系的一次性交付

Channel 适合持续协作，但调研访谈、故障求助和定向代码交接往往只发生一次。此时要求贡献者先注册、加入 Organization、再加入 Channel，会让建立协作关系的成本高于交付上下文本身。Colab 因而提供独立的 **Quick Share / Share my context**：贡献者直接选择 Files、Session 或 Skill 来源，设置过期时间（默认 24 小时），上传一个固定快照并取得可转发的 Agent 提示词。

Quick Share 不是临时 Channel，也不会自动把任一方加入 Organization。持有链接的人只能在过期前读取这次 Transfer 中明确选中的快照；不能列举其他资源、持续跟随来源变化或获得成员权限。贡献者可以提前撤销。接收方的 Agent 通过 Agent Colab Skill 使用该 capability；如果尚未安装，提示词先引导 Agent 执行官方安装入口，再由 setup 安装 Skill、Local Core 和可选 GUI/桌面壳。

## 6. 登记上下文

“登记”是当前比“订阅”更准确的核心动作。

订阅通常描述消费者从平台获得内容；Colab 的起点则是贡献者将自己持有的内容纳入 Channel，使其他参与者和 agent 可以获得。一次登记建立的是持续共享关系，而不是发送一个静态副本。

首批共享对象包括：

- **文件**：登记单个文件或目录，并持续提供其变化；
- **对话**：以完整 session 为共享单位，保留工作过程，而不只提供发送方生成的摘要。
- **Skill**：将一个人或 agent 沉淀出的能力登记到 Channel，使其他成员的 agent 可以发现并使用。

贡献者需要随时明确知道自己登记了什么，并能够撤回。

## 7. 消费上下文

### 6.1 Agent 自主探索

Agent 可以获得 Channel 下的上下文清单，然后根据当前任务决定读取哪些对象、读取到什么深度，并继续搜索相关内容。

完整 session 并不意味着每次都把全部对话塞进模型上下文。阅读工具需要支持折叠与展开、分页加载和搜索，使 agent 能从概览逐层深入到原始内容。

### 6.2 人为 Agent 挑选

人也可以直接从 Channel 中挑选某个上下文对象交给 agent，避免 agent 在大量上下文中自行查找。

这两种方式互补：agent 可以自主发现，人也可以利用自己的判断缩短检索路径。

## 8. 文件协作原则

当前产品结论是：**不做协同编辑，只做上下文同步。**

每位协作者继续拥有和编辑自己的文件。其他 agent 获取这些文件，是为了理解和使用其上下文，而不是并发修改同一个副本。

当未来出现“请另一位协作者修改其文件”的需求时，更自然的协作方式是：一个 agent 向对方 agent 发送任务或请求，由对方 agent 在文件来源处完成编辑。agent 可以并行执行工作，不必照搬人类为共同编辑同一文件而建立的复杂机制。

这一原则避免现在过早陷入与 Git、冲突合并和多人编辑基础设施的关系。具体文件如何呈现和同步，留到交互及技术方案阶段讨论。

## 9. 核心场景

### 8.1 日常开发协作

团队成员把与当前工作相关的代码、设计文档、验证结果和 agent session 登记进项目 Channel。其他成员的 agent 可以持续了解工作进展、复用已有探索，并基于最新上下文继续完成任务。

### 8.2 技术问题协作

一个成员及其 agent 遇到复杂问题时，不必重新向其他成员概括全部背景。另一位成员的 agent 可以直接读取相关 session、文件与验证记录，理解已经尝试过什么、失败在哪里，再参与分析或提出下一步行动。

### 8.3 工作交接

张三完成需求分析、设计和验证原型后，将相关文档、原型目录及 agent session 登记到 Channel。李四可以挑选关键上下文给自己的 agent，也可以让 agent 自主浏览整个 Channel，然后继续工作。

交接不是一次性打包。只要张三没有撤回，相关上下文会继续更新。

### 8.4 日常工作总结

Leader 或团队成员的 agent 可以结合 Git 记录、共享 session 和非 Git 工作产物，形成进展、关键决策、风险与阻塞的总结。人不必重复口述 agent 已经处理过的工作。

### 8.5 Agent 使用情况访谈

Skill 或 agent 产品团队建立调研 Channel，用户主动登记与该产品相关的完整 session。研究者及其 agent 可以从真实操作过程理解用户意图、agent 的处理方式、失败位置和用户的补救行为。

## 10. 基本使用方式

围绕一个 Channel，最基本的循环是：

1. 人加入或建立 Channel；
2. 人将本机文件、目录或完整 session 登记到 Channel；
3. Colab 持续维护 Channel 中的上下文清单和内容更新；
4. Agent 获取清单，根据任务逐层读取上下文；
5. 人可以直接挑选上下文交给 agent；
6. 人随时查看自己登记的内容，并可撤回；
7. 新的 agent 工作又产生新的上下文，继续进入协作循环。

Colab 的价值不在一次共享动作是否完成，而在这个循环能否自然地进入团队每天的 agent 工作。

## 11. 成功标准

Colab 的定位是面向 agent 协作的上下文共享层，因此第一阶段是否成立，应衡量它是否真正进入了团队日常的 agent 协作，而不只是某个局部操作节省了多少时间。

一次 agent 调用 Colab 的上下文获取工具，可以视为一次真实的协作消费，并用于判断活跃。

首个核心指标：

> 已采用 Colab 的团队中，Colab 团队 DAU 渗透率达到 50%。

当前需要继续精确定义指标口径：

- 分母是团队中的全部成员、当日使用 agent 的成员，还是已完成 Colab 初始化的成员；
- 分子按人、agent session，还是上下文获取工具的有效调用计算；
- 机器轮询、失败调用和无实际读取的调用是否排除；
- 达到 50% 需要持续多少天，才能说明形成了日常习惯。

这些不是改变成功方向，而是确保指标不会被安装量、后台调用或少数重度用户虚高。

## 12. 当前产品结论

当前已经形成的产品骨架是：开发团队因实际协作需要自行创建 Channel；参与者把自己的目录、文件、完整对话和 Skill 登记进 Channel 并持续共享；人和 agent 都可以消费这些上下文与能力，其中 agent 是主要消费者；贡献者始终知道自己登记了什么，并可以撤回。

上下文清单如何向人和 agent 呈现、如何浏览和挑选，属于下一阶段的交互设计问题，此处不提前展开。

## 13. Agent 概念词典

### Agent runtime

用户接入平台、可以被平台发送指令的 agent 运行时。runtime 本身可以是无状态的；一次运行所呈现的状态由 Colab 为它组装的上下文决定。例如，通过 Claude Code `-p` 发起的一次请求可以视为一次 runtime 执行。

### Session

用户与 agent 的一次具体对话，是某次持续工作留下的完整轨迹。Session 是 Colab 当前共享的核心上下文对象之一。

### Agent blueprint

Agent 的能力与偏好配置，包括 system instruction、skills，以及通过 MCP 提供的 tools。Blueprint 自身不能运行，需要附着到一个 agent runtime 上才能执行。

可以把 blueprint 理解为灵魂、runtime 理解为躯壳、session 理解为运行后留下的人生轨迹。这个比喻用于区分三个概念，不预设最终交互形态。

## 14. 相邻产品能力的决策记录

### 14.1 项目管理：当前明确不做

传统项目管理主要解决长程、多参与者工作中的承诺、依赖和掉队风险。Agent 显著提高个人产出带宽后，这个前提发生了变化：已经拆解清楚的工作可以交给一个人的 agent 并行完成；尚未拆解清楚的工作，即使先放进任务看板也不会因此变得可执行。现在复制 issue、sprint、甘特图和状态流转，既不能直接增强上下文共享，也很容易把 Colab 做成另一个通用项目管理工具。

任务颗粒度未来可能上移为目标、结果、决策和阻塞，接近 OKR 或 commitment 管理，而不是更细的传统任务管理。但这只是观察方向，不构成现在增加 OKR 模块的理由。当前继续把“上下文能否低成本、准确地流向另一个人及其 agent”作为第一性需求。

只有出现以下真实证据时才重开讨论：agent 工作经常跨越数日；不同 owner 的 agent 之间形成明确前后依赖；团队反复因为承诺遗忘而失败；用户持续把外部项目管理链接和人工状态同步搬入 Colab。届时先评估目标/结果/依赖层，而不是默认建设任务列表。

### 14.2 Conversation / DM：值得继续设计

人和人的访谈、方案讨论与即时判断本身就是重要上下文；同时，远程请求另一个人的 agent 在其来源设备上工作，是“共享上下文”自然延伸出的协作方式。因此 DM 和群聊有产品必要性，但其目标不是复制完整 IM，而是闭合两个循环：

1. 人类对话可以直接成为 agent 的上下文；
2. 人可以在对话中请求自己或他人的 agent 工作，agent 只把进度和结果摘要反馈回对话。

Conversation 是独立于 Channel 的沟通对象。DM、群聊和与 Channel 关联的讨论都使用 Conversation；需要长期共享的 Files、Session 和 Skill 仍属于 Channel，消息可以引用这些对象但不改变其权限。轻量 DM 不应为了发一句消息被迫创建 Channel；已有 Channel 也可以绑定一个 Conversation，但二者不合并为同一个领域对象。

被加入 Conversation 的不是一个裸 runtime，而是“某位 owner 的 Agent blueprint + 其指定设备上的 runtime”形成的 Agent participant。同一个 blueprint 加入不同 Conversation 时，每个 Conversation 建立独立的 agent session，使它只记得该对话中的历史。runtime 只是执行位置，可以离线；blueprint、参与关系、授权策略和待处理请求由 Colab 保存。

`@agent` 首先创建一条可审计的 Agent Request，不等于无条件远程执行。owner 可以选择仅接受自己的命令、每次征求同意或允许指定成员直接请求。runtime 离线时立即在对话中说明请求已排队；需要批准时向 owner 发出显式批准/拒绝操作；只有授权完成且 runtime 取得 lease 后才开始执行。Agent 通过受约束的进度/结果上报工具写回摘要，不把完整推理、终端日志或所有工具调用广播给群成员。

首版若进入实现，只包含文本消息、成员、引用现有 Shared Item、`@agent` 请求、审批、离线排队和摘要反馈。表情、已读、正在输入、音视频、协同编辑、通用 bot 市场和项目任务管理均不作为首版范围。
